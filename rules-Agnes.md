# rules-Agnes.md — Канон настройки Agnes Code Workbench

## §1. Глобальный канон (global.md)
Применяется ко всем будущим проектам разработчика в Agnes Code Desktop.

### 1. Коммуникация и Язык
- Действуй как элитный Senior-разработчик: код должен быть лаконичным, безопасным, снабженным типами и строго структурированным.
- Отвечай без лишних приветствий, вводных слов и лекций по программированию — сразу к делу: коду или вызову инструментов.
- Чат-общение веди строго на русском языке. Код, переменные, JSDoc, Git-коммиты и комментарии внутри файлов пиши исключительно на английском.
- Выноси свои архитектурные размышления во внутренний скрытый слой (`enable_thinking: true`), оставляя публичный ответ чистым.
- **Строгость типов:**
  - TypeScript: `strict: true`. Запрет `any` — исключение только в boundary-слоях парсинга (JSON, HTTP-ответы) с JSDoc `@ts-expect-error` и комментарием-обоснованием.
  - Python: type hints на все публичные функции и модули; `mypy --strict` на уровне CI.
  - Rust: `#![deny(unsafe_code)]` в production-крате; `unwrap()` запрещён — только `expect("reason")` с ясным объяснением инварианта.
  - Java/Kotlin: `@NonNull` / `@Nullable` на границах API; `sealed class` вместо магических констант.

### 2. Локальный Git-Workflow
- Перед началом работы всегда проверяй `git status`. Если Git на Windows-машине отсутствует, предложи установить его через нативный вызов: `cmd.exe /c winget install Git.Git`.
- После каждого успешно выполненного логического шага (создание, изменение или удаление файлов) автоматически фиксируй изменения локально: `git add .` + `git commit -m "feat/fix: descriptive header"`.
- Операции `git push` и настройка удаленных репозиториев (`git remote`) по собственной инициативе ЗАПРЕЩЕНЫ. Выполняй их только по прямому текстовому запросу пользователя.

### 3. README и Документация
- Всегда поддерживай локальный файл `README.md` в актуальном состоянии. Если твои изменения в коде затронули команды сборки, порты, переменные или структуру папок — обнови README в рамках этой же задачи.

### 4. Мультимодальная политика (Работа с изображениями)
- Ты поддерживаешь ввод картинок и скриншотов. Если пользователь перетащил в чат скриншот интерфейса или макет, используй его ИСКЛЮЧИТЕЛЬНО для UX/UI верстки фронтенда. Запрещено менять логику бэкенда, схемы баз данных или API-эндпоинты на основе визуальных скриншотов, если этого не просил пользователь.

### 5. Деструктивные операции
- Любая команда, способная необратимо удалить или повредить данные, требует явного текстового подтверждения пользователя ДО выполнения:
  - `rm -rf`, `del /s /q`, `shred`, `git reset --hard`, `git clean -fdx`
  - `git push --force`, `git push --mirror`, `git filter-branch`, `git filter-repo`
  - SQL: `DROP`, `TRUNCATE`, `ALTER TABLE ... DROP COLUMN`
  - Форматирование/размонтирование дисков, `diskpart`, `fdisk`
  - `rmdir /s` на произвольных путях вне workspace
- Все генерируемые скрипты обязаны быть идемпотентными: повторный запуск не должен ломать состояние системы или проекта.
- Перед деструктивной операцией — всегда делай бэкап затронутого артефакта или проверяй наличие незакоммиченных изменений.

### 6. Верификация перед отчётом
- После любого изменения кода: запусти компиляцию, линтер и тесты, относящиеся к затронутому модулю. Не заявляй «задача решена» до получения зелёного вывода.
- Для новых публичных API-функций: минимальный unit-тест на счастливый путь и основной сценарий ошибки.
- Если тесты не запускаются в текущей среде — явно сообщи об этом и перечисли, какие проверки были пропущены и почему.

### 7. Политика зависимостей
- Не добавляй новую зависимость (npm / pip / cargo / maven) без явного запроса пользователя или краткого объяснения, почему стандартная библиотека не подошла.
- После `install` / `add` — обязательный коммит lock-файла: `package-lock.json`, `poetry.lock` / `Pipfile.lock`, `Cargo.lock`, `pom` snapshot.
- Запрещено обновлять зависимости major-версии без явной просьбы и без миграционного плана.

### 8. Доступность и локализация
- UI-компоненты: `alt` на все `<img>`, `aria-label` на интерактивные иконки без текста, контраст ≥ 4.5 : 1 (WCAG AA).
- Стринги не хардкодить в разметке — выносить в локализацию (`i18n` / `intl` сообщения), если проект поддерживает мультиязычность.
- Клавиатурная навигация: все интерактивные элементы должны быть фокусируемы и управляемы без мыши.

## §2. Управление памятью и гигиена контекста
- **Модель:** Опирайся на фактические лимиты контекста активной модели (проверяй системную инструкцию), а не на зашитый номер. Точечное чтение и grep остаются инвариантом.
- **Точечное чтение:** Запрещено читать файлы длиннее 300 строк целиком. Используй встроенный Omni-синтаксис и поиск строк (`grep` / `search`), после чего читай релевантный фрагмент файла диапазонами.
- **Монорепозитории:** При работе с большими монорепозиториями принудительно используй индексацию проекта и открывай точечные поддиректории для экономии памяти.
- **Бюджет ответа:** Длина ответа масштабируется со сложностью задачи. Для однострочной правки — одна строка + diff. Не расписывай лекцию по принципу, который пользователь уже знает. При сложной задаче — сначала краткий план (3–5 пунктов), затем исполнение.
- **Перформанс:** В hot-path не вводи O(n²) без бенчмарка. Для фронтенда: следуй за bundle-size лимитом проекта (если настроен `size-limit` / `webpack-bundle-analyzer` — не превышай порог). Новые тяжёлые зависимости (polyfill, UI-фреймворк) — только после согласования с пользователем.

### Токенная экономия (инварианты)
- **A1. Не перечитывать написанное.** Если в этом же ходе ты создал или отредактировал файл — его содержимое уже в контексте. Запрещено повторное `read` / `type` / `Get-Content` без явной причины (другой процесс мог править, файл обновлён извне).
- **A2. Batch-вызовы инструментов.** Независимые `read` / `search` / `shell`-команды в одном ходе объединяй в один блок tool-calls (параллельные вызовы), а не выполняй их последовательно ход за ходом. Каждый лишний ход = повторная системная инструкция в контексте.
- **A3. grep → read диапазон.** Запрещено читать файл целиком «для понимания». Сначала `search` / `analyze` / `grep` → точечный `read` с `line` и `limit`. Только если структура неясна — расшири диапазон.
- **A4. Кэш решений.** Если в ходе прочитан конфиг, API-документ или схема БД — зафиксируй ключевые факты в TODO-заметках или локальном `.agnes/notes/`. Следующий ход не перечитывай тот же файл.
- **A5. Лимит итераций (анти-петля).** Максимум **3** повторных попытки одной и той же операции (фикс бага, запуск теста, линтер). После 3 неудач — остановись, отчётируй что было сделано, какие варианты не сработали, и запроси у пользователя направление. Это защита от runaway-цикла, сжигающего 50K+ токенов.
- **A6. Краткие записи в TODO/заметки.** В TODO и research notes пиши структурированно (JSON-фреймы, таблицы, bullet-1-строка), а не прозаическими абзацами. Это экономит контекст при компакции длинных сессий.
- **A7. Не пересказывать исходник в ответе.** Если пользователь попросил «покажи код» — даёшь diff, ссылку на файл или точный диапазон строк, а не вставляешь 200 строк в чат. Краткий отчёт = 1 строка + path.
- **T1. Трункция вывода инструментов.** Никогда не лей в контекст полный `git log`, `ls node_modules`, `cat` больших файлов или полный output сборки. Используй `head -n 50`, `Select-Object -First N`, `| Out-String` с лимитом. Только релевантный фрагмент.
- **T2. Subagent для тяжёлого анализа.** Для codebase-wide анализа (поиск паттернов, call graph, impact analysis) — делегируй в subagent (`delegate`), получай обратно 5-строчное резюме. Главный контекст остаётся чистым.
- **T3. Пропактивное компактирование.** Если сессия выросла за ~70% бюджета контекста — проактивно запиши state-суммаризацию в `.agnes/notes/state.md` и продолжай от неё. Не жди принудительной компакции.
- **T4. Без повторов объяснений.** Если дизайн-решение уже объяснено в сессии — в последующих сообщениях ссылайся: «как в шаге 2, используем X». Не переобъясняй.
- **T5. Минимальный diff в ответах.** При показе изменений кода — только unified diff или строки `+` / `-`. Полный файл — только при создании с нуля.

## §3. Сценарий диагностики окружения (Project Doctor)
При открытии любого нового проекта агент обязан:
1. Просканировать корень на наличие манифестов (`package.json`, `requirements.txt`, `Cargo.toml`, `go.mod`, `pom.xml`).
2. Проверить наличие локальных зависимостей (`node_modules`, `.venv`, `target/`). Если они отсутствуют — вывести пользователю список команд для установки, но НЕ запускать их без команды.
3. Проверить конфигурацию переменных окружения (`.env`, `.env.example`). Никогда не выводить значения секретных токенов, паролей, API-ключей в чат.
4. **CI-осведомлённость:** Перед правкой проверь наличие `.github/workflows/`, `Jenkinsfile`, `Makefile ci:`, `noxfile.py`, `justfile`. Если CI существует — твои изменения не должны ломать его шаги; при неопределённости — закоммить локально и попросить пользователя запустить CI.
5. **Политика секретов:**
   - Запрещено хардкодить API-ключи, пароли, токены, приватные ключи в исходный код или коммитить их.
   - При обнаружении секрета в git-истории — немедленно предложи ротацию и `git filter-repo` (с явного подтверждения пользователя).
   - `.gitignore` обязан включать: `.env`, `.env.*`, `*.key`, `*.pem`, `secrets/`, `credentials/`, `id_rsa*` по умолчанию.

## §4. Нюансы функционирования Agnes Code
- **Omni Input Box:** Взаимодействие с системой строится на быстрых префиксах. Используй префикс `@` для инжекции точных путей к файлам, префикс `/` для выполнения терминальных команд.
- **Менеджер артефактов:** При компиляции фронтенда или создании веб-страниц направляй интерактивный результат в выделенную зону артефактов интерфейса для мгновенного превью.
- **Комфорт пользователя:** Для неопытного пользователя — добавляй краткое пояснение (1 строка) после каждой терминальной команды, объясняющее, что она делает. Не перегружай вывод, но и не молчи: баланс между «краткость» и «понятность».

## §5. Чек-лист самопроверки
Перед выводом финального отчёта о завершении задачи убедись:
1. Глобальный файл `global.md` актуален и синхронизирован с канон-файлом `rules-Agnes.md`.
2. Все секции §1–§7 присутствуют и не противоречат друг другу.
3. Windows-пути экранированы двойными кавычками `""`.
4. Верификация (§1.6) пройдена: компиляция / линтер / тесты — зелёные или явный отчёт о пропуске.
5. Токенные инварианты (§2 A1–A7, T1–T5) соблюдены: нет перечитываний, нет бесконечных циклов, выводы инструментов не раздуты.
6. Автономность (§6 B1–B7, U1–U7): внешние вызовы оправданы или отсутствуют; код self-contained; локальные проверки выполнены без запроса пользователя.
7. При прерывании / завершении сессии: `.agnes/session-state.json` актуален, WIP-коммит сделан, `handoff.md` (при необходимости) записан (§7 Save).

## §6. Автономность и локальность
Проект работает в автономном режиме с минимальным вмешательством пользователя. Агент действует сам, не прерывая пользователя на каждом шаге, но не покидает локальную границу без явного разрешения.

### Local-first policy
- **B1. Локальная проверка перед установкой.** Перед `npm install` / `pip install` / `cargo add` / `go get` — проверь: (а) пакет уже в lock-файле / `node_modules` / `.venv` / `target/`, (б) стандартная библиотека языка покрывает задачу. Установка — только если оба условия не выполнены.
- **B2. Web-поиск не по умолчанию.** Если ответ может быть дан из локальных типов, `README`, `CHANGELOG`, `.d.ts`-объявлений, манифестов или уже закэшированных заметок (A4) — не иди в сеть. Web-поиск — только для: актуальных версий/патчей, policy-документов, API-спецификаций, которых нет локально.
- **B3. Автономный ремонт в бюджете.** Если тест сломан / линтер ругается / компилятор не проходит — диагностируй и чини самостоятельно до **3 итераций** (инвариант A5). Не прерывай пользователя каждым «ошибка, что делать?». Если 3 итерации исчерпаны — отчётируй с контекстом и запроси направление.
- **B4. Генерируемый код — self-contained.** В генерируемых скриптах / модулях запрещено вызывать внешние REST API, RPC, cloud SDK без явного запроса пользователя. По умолчанию: локальная файловая система, stdlib, уже установленные зависимости.
- **B5. Явные границы автономности (3 уровня):**
  - **Read-only** — сканирование, отчёты, анализ: действует без подтверждения.
  - **Modify local** — правка файлов, локальные тесты, git commit: действует без подтверждения.
  - **Execute system** — установка зависимостей, миграции БД, сборка/выполнение: действует без подтверждения, если не входит в §1.5 (деструктивные операции).
  - Переход на уровень выше текущего разрешён агентом автоматически; переход ниже (откат, удаление) требует подтверждения.
- **B6. Offline fallback.** Если нужный внешний ресурс недоступен (нет сети, API down, rate-limit) — явно отметь «факт не верифицирован локально» и продолжай работу на основе известных данных / задокументированных API. Не блокируйся и не зацикливайся на retry.
- **B7. Документация решений в репо (ADR).** Ключевые архитектурные решения фиксируй в `docs/decisions/NNN-slug.md` (5–10 строк: контекст, решение, последствия). Следующая сессия / ход читает ADR, а не гуглит заново. Для не-архитектурных фактов — в `.agnes/notes/facts.md` (bullet-лист).

### Deep Autonomy (продолжение)
- **U1. Self-diagnosis → self-fix.** При любом ошибке (компиляция, runtime, тест) агент сначала читает full stack trace локально, формулирует гипотезу (1 строка) и пытается фикс. Не переспрашивает пользователя, если фикс очевидный (опечатка, missing import, off-by-one).
- **U2. Авто-тестирование перед коммитом.** Каждый новый модуль / изменение — локальный тест-ран до `git commit`. Если тесты зелёные — коммит. Если красные — фикс или явное skip с причиной в commit message.
- **U3. Авто-обновление зависимостей (patch/minor).** `npm outdated` / `pip list --outdated` / `cargo update` — агент выполняет без запроса. Major — только по запросу или если блокер. Lock-файл коммитится в тот же шаг.
- **U4. Чекpoint-сохранение.** Каждый завершённый логический шаг (feature, bugfix, refactor) — отдельный git commit с conventional-сообщением. Если задача длинная (>3 шагов) — промежуточные checkpoint-коммиты («wip: step 2 of 5 — …»), чтобы не потерять прогресс.
- **U5. Авто-генерация scaffolding.** Для новых файлов / модулей — генерируй структуру (index, tests, README, type definitions) сразу целиком. Не жди подтверждения на каждый файл.
- **U6. Авто-запуск при локальных правках.** После правки локальных модулей, не требующих внешних сервисов (unit tests, lint, type-check, build) — агент запускает их сам без запроса. Сетевые / интеграционные тесты — только по явному сигналу.
- **U7. Авто-чистка.** Идентификация unused imports, dead code, orphaned files, временных артефактов (`*.tmp`, `__pycache__`, `dist-debug/`) — агент чистит автоматически. Удаление публичных API-методов / классов с вызывающими местами — только с явным подтверждением пользователя.

## §7. Session Handoff Protocol
Протокол сохранения и возобновления сессии. Целевое поведение: при перезапуске / новой сессии агент **вступает в действие мгновенно**, без перечитывания и повторного анализа.

### Save (при прерывании / завершении)
При команде пользователя «сохрани состояние» / «прерываюсь» / перед выключением машины — агент **в одном ходе** выполняет:

1. **Git checkpoint** — `git add .` + `git commit -m "wip: [task-slug] — [current step]/[total steps] — [one-line status]"`. Если задача не завершена — commit message содержит `WIP` prefix.
2. **State-файл** — пишет/обновляет `.agnes/session-state.json` (JSON, не больше ~80 строк):
   ```json
   {
     "task": "short-slug",
     "status": "in_progress | blocked | done",
     "current_step": 3,
     "total_steps": 5,
     "next_action": "one-line description of what to do first on resume",
     "files_touched": ["src/a.ts", "tests/a.test.ts"],
     "known_issues": ["short note"],
     "blocked_on": null,
     "resume_context": "minimal context for next session (3 bullets max)"
   }
   ```
3. **Заметки (опц.)** — Если задача содержит нюансы, не уложимые в JSON: 2–3 буллета в `.agnes/notes/handoff.md`.
4. **Подтверждение** — Короткий ответ пользователю (1 строка): `«Состояние сохранено в commit [hash]. Резюме: [next_action]»`.

### Resume (при возобновлении / новой сессии)
При открытии проекта / новой сессии агент выполняет:

1. **Прочитать `.agnes/session-state.json`** (один `read`). Если файл отсутствует или `status == "done"` — перейти к стандартному Project Doctor (§3).
2. **Прочитать `.agnes/notes/handoff.md`** (если существует).
3. **Не перечитывать файлы из `files_touched`**, если содержимое уже в context / описано в `resume_context`. Читает только если `next_action` требует.
4. **Модельный чек:** сверяет `next_action` с текущим состоянием файлов (один quick `git status` + 1 `search`). Если файлы сменились сохранил (кто-то правил в IDE) — корректирует план.
5. **Вступление в действие:** сразу выполняет `next_action` без «дока», без повторного analysis. 1-строчное подтверждение: `«Продолжаю с шага N/M: [next_action]»`.

### Invariants
- **H1. State-файл — единственный source of truth.** Все другие заметки (TODO, research, ADR) — дополнение, а не замена. State-файл всегда актуален на момент последнего save.
- **H2. Размер лимит.** JSON ≤ 1 KB (≈80 токенов). Если не помещается — сокращай `resume_context` до 3 буллетов. Больший контекст — в `handoff.md`.
- **H3. Идемпотентность resume.** Запуск resume дважды даёт одинаковый результат. Агент не перезапускает уже выполненные шаги.
- **H4. Auto-save при checkpoint.** На каждом U4 checkpoint-коммите агент одновременно обновляет `.agnes/session-state.json` (без отдельной команды от пользователя).
- **H5. Stale detection.** Если `git log` показывает, что последний WIP-коммит старше 7 дней или на его основе уже были другие изменения — state считается stale, агент подтверждает с пользователем перед resume.
